02P0 · 会真出问题，已全部修复

这两条不是风格问题，是会在真实使用中造成困惑或数据丢失的问题。均已修复并附验证结果。

已修复

工具清单存在三份，且已经不一致

同一份"90 个工具"的数据，被维护在三个地方：config.json、MainWindow.xaml.cs 的 AllTools 字段、AppConfig.AddDefaultTools()。后两者是运行时兜底，但已经和 config.json 分叉了。

config.json: 90 条  |  MainWindow.AllTools: 86 条  |  AppConfig 默认清单: 86 条

差异具体是：config.json 里多了磁盘精灵（32位）.NET Framework 4.7.2MicrosoftEdgeSetup希沃优化工具，而代码里多了一个自动更新时间（名字不一样，实际是同一个工具）。

后果：一旦用户弄丢配置（U 盘拷贝漏了、杀软误删、写入失败），程序会静默重建一份 86 条的另一套清单——工具名和路径都对不上，用户看到的是"我的工具箱少了几个工具，还多了个陌生的"。

这不是推测，已经实测复现：把 bin 目录里的 config.json 删掉再启动，改动前生成的是 86 条，与仓库里的 90 条差 5 个名字。

改法：代码里不再保存任何工具/分类清单，config.json 成为唯一来源。缺失或损坏时，从编译时嵌入程序集的同一份 config.json 里重建——模板就是发布时的那份数据，不可能再分叉。

// 删掉的两处（共 128 行数据）
private ToolInfo[] AllTools = [ new("酷我音乐", ...), ... ];  // 111 行
private static void AddDefaultTools(AppConfig config) { ... }  // 184 行

// csproj —— 把 config.json 同时作为资源嵌入
<EmbeddedResource Include="config.json" LogicalName="config.json" />

// AppConfig.Load() —— 缺失/损坏时的唯一兜底路径
using var stream = typeof(AppConfig).Assembly.GetManifestResourceStream("config.json");
return JsonSerializer.Deserialize<AppConfig>(new StreamReader(stream).ReadToEnd());

同时补上了"如实告知"：重建过的配置会在状态栏提示「config.json 缺失或损坏，已用内置模板重建；自定义过的工具需要重新添加」，而不是让用户自己发现工具变少了。

验证场景结果
删除真实程序的 config.json 后启动 → 重建 90 条（端到端）通过
JSON 语法损坏 → 仍能重建 90 条通过
categories 为空数组 → 仍能重建 90 条通过
配置正常时不触发重建，读取结果不受影响通过
重建后的 config.json 不泄漏内部标记字段通过

代码里现存 new(" 仅剩 1 处——"all" 这个虚拟分类，不属于工具数据。

已修复

删除工具：顺序是反的，且不可恢复

原实现先改配置、再删文件：

_config.RemoveTool(t.RelativePath);          // ① 立刻写盘，配置条目已消失
if (File.Exists(path)) File.Delete(path);   // ② 这里一旦抛异常（工具正在运行）
// 结果：列表里没了，文件还在 → 变成"孤儿文件"

两个操作没有事务性，失败一半就进入不一致状态。只把 File.Delete 换成"送回收站"是治不好的——文件能捞回来，但 config.json 里的条目早没了，恢复回来也不会出现在界面上。

改成了「自带回收站 + 单条记录绑定」：

// 顺序反转：先搬文件，搬不动就整体中止，配置原封不动
if (!MoveIntoTrash(src, id)) return false;   // 文件被占用 → 失败返回
category.Tools.Remove(tool);                  // 再改内存
Trash.Insert(0, new TrashEntry { Id = id, ... });
Save();                                       // 最后一次原子落盘

文件进 回收站/<id>/，配置条目进 config.json 的 trash 数组，共用同一个 id，所以恢复是真正的一步到位：文件移回原位 + 条目挂回分类。删除分类同理，整个目录连同其下所有工具配置一起暂存。

入口有三处：删除后状态栏 15 秒内可点「撤销」；设置 → 回收站 可恢复最近一项或清空；配置文件里带 deletedAt，跨机器拷贝也能恢复。

测试场景结果
删除后文件离开原位、配置条目消失、实体进回收站通过
重启程序后仍能恢复（跨进程持久化）通过
恢复后路径、分类归属、描述完全还原通过
原位置已有同名文件时，恢复不覆盖（自动改名为「xx (恢复1)」）通过
文件被进程占用时删除：返回失败，配置不改，不产生脏数据通过
清空回收站：实体目录删除 + trash 数组清空通过

上述 6 组共 29 项断言已用独立测试工程跑通，非人工点击验证。

08schema v2：稳定身份 + 路径自愈

前两批解决了"能不能改"，这一批解决"改了之后会不会断链"——以及文件被搬走之后还能不能找回来。

根因

拿 relativePath 当主键，一切改名都无处落地

之前的 ToolConfig 只有三个字段：name / description / relativePath。所有定位都靠路径：RemoveTool 按路径找、AddTool 按路径查重、回收站按路径恢复。

后果很具体：分类没法改名——一旦把 工具\CPU工具 改成 工具\CPU检测，该分类下 20 条工具的路径全部失效，界面上一片空白；回收站恢复也不可靠——只能按名称猜回哪个分类，同名分类就猜错。

这不是"设计不够优雅"，是功能性缺失：重命名分类这个需求，在旧模型下根本写不出来。

已实现

分类与工具各配一个 id，路径降级为"定位信息"

12 位十六进制（Guid.NewGuid().ToString("N")[..12]），够短、够避免碰撞。语义划分变得清晰：

字段现在负责什么
id身份：改名、搬目录、删除再恢复，都是同一个东西
relativePath定位：文件此刻在哪。可以被改写，不再是主键
name显示名：随时可改，删掉也不影响任何关联

回收站条目同时记下 toolId 与 categoryId，恢复时沿用原 id——一次删除不该改变对象的身份。

路径失效后自动重连：按「文件名 + 体积」在 工具\ 下找回

id 保住了身份，但文件位置仍然靠 relativePath 记着。用户在资源管理器里把 工具\某分类\某工具 拖到别处，这个工具就会从界面上消失——而且没有任何提示。

前提是得先知道"原来那个文件多大"。所以配置里新增 size 字段：每次启动时对存在的文件做一次 stat（90 次，耗时可以忽略），值变了就更新。文件已经不见的条目保持旧值不动——那正是之后要拿来比对的基准。

匹配规则：

条件行为
同名 + 同体积，且全树只有 1 个认领
同名同体积有 2 个以上放弃，记入日志「候选不唯一」
同名但体积都对不上放弃，多半是被换成了新版本，不算同一个工具
体积未知（旧配置且启动时文件已丢）仅当同名文件全树唯一时认领，汇总日志里会标出"其中按名字匹配（体积未知）N 个"
候选已被其他工具登记跳过，绝不把 A 的地址让给 B
候选位于别的目录型工具内部跳过（unins000.exe、内置的 7z.exe 这类不该被认领）
目录型工具（路径无扩展名）按目录名匹配，同样要求全树唯一

执行顺序：先重连、再扫描未收录。反过来会出问题——路径没修的话，被搬走的工具会被"未收录扫描"当成新工具再收一遍，于是同一个程序在清单里出现两条。
